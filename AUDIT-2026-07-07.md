### ARH-01 · 🔴 CRITIC · `backend/service/src/fleet/fleet.service.ts:229`

**Soft-deleting a device permanently bricks that phone's fleet comms (unique violation 500 loop on re-registration)**

- **Arie:** device registry  ·  **Sursă:** finder `arch-fleet-comms`  ·  **Încredere (self-report):** high
- **De ce e o problemă:** devices.device_uuid is a hard UNIQUE (supabase/migrations/00055_fleet_devices.sql:53) over ALL rows, but checkin() looks up with `deleted_at IS NULL` (fleet.service.ts:209). After an admin calls DELETE /super-admin/devices/:id (soft delete, fleet.service.ts:1323-1329), the phone's next check-in sees no row, takes the registration branch, and the INSERT at line 229 hits the unique constraint on the soft-deleted row -> 500. The phone retries every ~60s forever; it can never re-register, never receives OTA/Tailscale/remote commands again. Recovery requires manual DB surgery or wiping SecureStore (factory reset on a Device-Owner phone). Admins deleting stale-looking device rows is a realistic operation.
- **Recomandare:** Replace the UNIQUE column constraint with a partial unique index `ON devices(device_uuid) WHERE deleted_at IS NULL`, and/or make registration an `INSERT ... ON CONFLICT (device_uuid) DO UPDATE SET deleted_at = NULL, device_token_hash = EXCLUDED.device_token_hash, ...` so a returning UUID resurrects the row and gets a fresh token.

### ARH-02 · 🟠 MAJOR · `backend/service/src/trip-requests/trip-requests.service.ts:196`

**confirm() is non-atomic and has no concurrency guard: duplicate aux machines + duplicate confirmation emails/SMS on concurrent confirm**

- **Arie:** trip-requests / atomicity  ·  **Sursă:** finder `arch-backend`  ·  **Încredere (self-report):** high
- **De ce e o problemă:** The pending-status check is a read at line 165 (findById), the aux-machine INSERT is at line 180, and the UPDATE at 196 has only WHERE id = ... with no AND status = 'pending' and no transaction. Two admins clicking Confirm (or a double-click landing on the two Swarm replicas) both pass the status check, mint TWO auxiliary machines rows, both UPDATE the request (last writer wins on machine_id/source_depot_id, possibly with different depots), and enqueue TWO 'transport-confirmation' jobs, so the driver and every notify recipient get duplicate emails and SMS. Also, if the UPDATE or messageQueue.add throws after the machine INSERT, an orphan aux machine is left behind (or the request is confirmed with no email ever sent, since the queue add at line 217 is the last step and there is no outbox record yet).
- **Recomandare:** Wrap the whole confirm in db.transaction() and make the status transition atomic: UPDATE trip_requests SET status='confirmed', ... WHERE id=... AND status='pending' RETURNING *, throw 400 when 0 rows returned, and only INSERT the machine + enqueue the job when the guarded UPDATE won. Enqueue the BullMQ job with a deterministic jobId (e.g. `confirm:${requestId}`) so a duplicate add is a no-op.

### ARH-03 · 🟠 MAJOR · `backend/service/src/sync/sync.service.ts:608`

**Sync mutation apply and sync_idempotency record are two separate statements, not one transaction — a crash between them permanently strands the mobile queue entry**

- **Arie:** sync / idempotency  ·  **Sursă:** finder `arch-backend`  ·  **Încredere (self-report):** high
- **De ce e o problemă:** applyMutation runs the entity INSERT/UPDATE (lines 526-604) and then a separate INSERT INTO sync_idempotency (line 608). If the replica dies between the two (SIGTERM during a Swarm rolling deploy, DB error, OOM), the write is committed but no idempotency row exists. The phone retries the same mutation: for an 'insert' the re-INSERT now hits the primary-key conflict on the entity table, throws, and push() returns status 'failed' — the mobile client marks that sync_queue entry failed forever even though the row IS on the server. This directly undermines invariant #2 (idempotency everywhere in sync) for the exact failure mode idempotency exists for.
- **Recomandare:** Wrap steps 2 and 3 of applyMutation in this.drizzleProvider.db.transaction(). Additionally, catch Postgres 23505 on the entity insert and translate it to status 'skipped' (fetch current sync_version) instead of 'failed', so replays of already-applied inserts self-heal.

### ARH-04 · 🟠 MAJOR · `backend/service/src/trip-requests/public-portal.controller.ts:36`

**Public 4-digit portal code endpoints have no rate limiting; each spam submission also fires synchronous Resend calls and alert rows**

- **Arie:** public portal / abuse  ·  **Sursă:** finder `arch-backend`  ·  **Încredere (self-report):** high

### ARH-07 · 🟠 MAJOR · `backend/service/src/geofence/geofence.service.ts:252`

**Geofence fire-once guards are SELECT-then-INSERT with no serialization across the two replicas — concurrent check runs produce duplicate approach/enter events and duplicate pushes**

- **Arie:** geofence / multi-replica race  ·  **Sursă:** finder `arch-backend`  ·  **Încredere (self-report):** high

### ARH-08 · 🟠 MAJOR · `backend/service/src/trip-requests/trip-requests.service.ts:220`

**message-send jobs run a multi-recipient fan-out inside one job with attempts:1 — a transient error mid-loop silently and permanently drops the remaining recipients**

- **Arie:** messaging / BullMQ design  ·  **Sursă:** finder `arch-backend`  ·  **Încredere (self-report):** high
- **De ce e o problemă:** Both enqueues use { removeOnComplete: true, attempts: 1 } (lines 220, 275). In TransportConfirmationProcessor (lines 236-267) and AvizNotificationService (157-192) each recipient is a sequential sendEmail/sendSms; ResendMessagingService.insertRow is a DB write that CAN throw (pool exhaustion, restart). If recipient 3 of 5 throws, the job fails with no retry: recipients 4-5 never get the confirmation, and because their outbox rows were never inserted, the /messages monitor shows nothing to retry — the loss is invisible. Adding attempts>1 naively would be worse: the retry re-runs the whole loop and double-sends to recipients 1-2, since nothing in the job is idempotent per recipient.
- **Recomandare:** Make the outbox the source of truth: in the processor, first INSERT all recipient rows as status='pending' (idempotently, keyed on request_id+kind+to_address), then send each pending row and mark sent/failed. Then attempts:3 with backoff is safe, and anything unsent is visible and retryable from /messages.

### ARH-12 · 🟠 MAJOR · `backend/service/src/sync/sync.service.ts:470-489 (idempotency check) together with apps/mobile/src/sync/push.ts:288-299 (mutation builder)`

**The real per-mutation idempotency key is generated and sent but never checked; the backend's actual dedup key collapses to (table, recordId) only**

- **Arie:** sync-idempotency  ·  **Sursă:** finder `arch-sync-logic`  ·  **Încredere (self-report):** high
- **De ce e o problemă:** sync.service.ts's idempotency lookup keys on `sync_idempotency (client_id, table_name, record_id, client_version)` — but mobile always builds mutations with `clientId: entry.entity_id` (i.e. clientId === recordId, not a device/client identifier) and `clientVersion: 0` (push.ts:296-297), hardcoded for every mutation regardless of table or history. The genuinely unique, randomly-derived `idempotencyKey` (`entry.idempotency_key`, e.g. `fuel_logs_<uuid>`) IS transmitted on the wire and validated by `syncMutationSchema` (packages/validation/src/dtos/sync-payload.schema.ts:11), but `sync.service.ts` never reads `mutation.idempotencyKey` anywhere — grep confirms zero references. Because the composite PK therefore reduces to (table, recordId) forever (client_version is always the literal value 0), the very FIRST mutation ever applied to a given record permanently occupies that PK row in `sync_idempotency`. Any SECOND distinct mutation later sent for the same record (an `update` or `delete`, both of which the type system, validation schema and backend `applyMutation` fully support) will match that stale idempotency row and be short-circuited as `status: 'skipped'` returning the OLD cached `result_data` — i.e. it is silently discarded and reported to the client as success. This directly violates the documented invariant '#2 Idempotency everywhere in sync: server checks sync_idempotency before applying' — it checks a broken key, not the mutation's actual identity. Today mobile only ever sends `action: 'insert'` through the generic push path (bale_productions/fuel_logs/consumable_logs; see FuelEntryFlow.tsx:153-172, ConsumableFlow.tsx, ProductionNumpad.tsx, FieldActiveNumpad.tsx) so the collision is latent, but the moment an edit/delete feature is wired to `/sync/push` for any of these tables (or bale_loads/task_assignments/machines/parcels, all of which already have full insert/update/delete handling in `applyMutation`), that mutation will be silently dropped forever.
- **Recomandare:** Use `mutation.idempotencyKey` (the actual per-operation UUID the mobile client already generates and sends) as the idempotency dedup key instead of (clientId, clientVersion). E.g. add a UNIQUE column/PK on `idempotency_key` in `sync_idempotency` and check/insert on that value; keep `client_version`/`sync_version` purely for optimistic-concurrency, decoupled from idempotency identity.

### ARH-13 · 🟠 MAJOR · `backend/service/src/sync/sync.service.ts:554-588`

**Generic push 'update' has no real optimistic-concurrency check — pure last-writer-wins; the protocol's 'conflict' status is dead code**

- **Arie:** sync-concurrency  ·  **Sursă:** finder `arch-sync-logic`  ·  **Încredere (self-report):** high
- **De ce e o problemă:** The update branch builds `SET ... WHERE id = recordId [AND organization_id = orgId]` with no comparison against an expected/base `sync_version` (or `clientVersion`), so any update unconditionally overwrites whatever is currently in the row — classic last-writer-wins clobbering if two actors (two devices, or a device vs. a REST/admin edit reusing the same table) race. `SyncResult.status` includes `'conflict'` and `apps/mobile/src/sync/push.ts:312` has a branch to handle it, but `sync.service.ts` never produces that status anywhere (grep for `'conflict'` only matches the dead client-side branch) — indicating the intended optimistic-lock/conflict-detection was either removed or never implemented, leaving the mobile-side conflict-handling code unreachable.

### ARH-14 · 🟠 MAJOR · `backend/service/src/sync/sync.service.ts:719-731`

**The sync_version out-of-order-commit stranding fix is applied only to `trips`; the other 7 syncable tables share the same global sequence and remain permanently exposed**

- **Arie:** sync-version-skew  ·  **Sursă:** finder `arch-sync-logic`  ·  **Încredere (self-report):** high
- **De ce e o problemă:** `sync_version` is a single global sequence (`sync_version_seq`, supabase/migrations/00040_global_sync_version.sql) assigned via a BEFORE trigger at statement time, not at commit time. Two concurrent transactions can therefore commit out of order relative to their assigned version numbers (a lower-numbered row committing after a higher-numbered one already visible), which is exactly the bug the code comment at sync.service.ts:719-727 documents for trips ('an in_transit trip at v21890 stranded behind a completed trip at v21891'). The fix — always re-sending non-terminal rows regardless of the cursor — is hard-coded to `table === 'trips'` only (line 729-731: `versionFilter = table === 'trips' ? ... : sql\`sync_version > ${sinceVersion}\``). `bale_loads`, `bale_productions`, `fuel_logs`, `consumable_logs`, `task_assignments`, `machines`, and `parcels` all use the plain `sync_version > sinceVersion` filter and share the exact same global sequence, so a row on any of those tables that commits late relative to its assigned version can be permanently skipped by every device's per-table delta cursor, with no error, no retry path, and no way to detect it client-side.
- **Recomandare:** Generalize the mitigation: either (a) apply a similar 'always resend recent/non-terminal rows' override per table where it makes sense, or (b) fix the root cause with a safe low-watermark approach — e.g. only advance a table's cursor to `now() - grace_period` worth of margin, or use `pg_current_xact_id()`/transaction-visibility-based watermarking instead of a plain sequence comparison, so late-committing lower-numbered rows are not skipped.

### ARH-15 · 🟠 MAJOR · `apps/mobile/src/sync/SyncManager.ts:39,57-62 and apps/mobile/src/lib/background-sync.ts:14-30`

**The sync mutex is a per-instance in-memory flag, not shared between the foreground app and the Android headless background-sync task**

- **Arie:** sync-concurrency  ·  **Sursă:** finder `arch-sync-logic`  ·  **Încredere (self-report):** medium
- **De ce e o problemă:** `SyncManager.syncInProgress` (SyncManager.ts:39) guards only calls made through the SAME `SyncManager` instance. `runBackgroundSyncCycle()` (apps/mobile/src/sync/run-background-sync.ts:69-85) constructs a brand-new `SyncManager` every invocation, and it is invoked both from the foreground app (periodic 60s / 2s-debounce / reconnect triggers via useSync.ts) and independently from the Android `expo-background-task` headless JS entry point (`background-sync.ts:14-30`), which can be scheduled by WorkManager while the app is also open and syncing in the foreground. ### ARH-16 · 🟠 MAJOR · `backend/service/src/fleet/fleet.service.ts:1028`

**One transient OTA failure permanently strands a device on the old version — server excludes 'failed' rows so the device-side 3-attempt retry never runs**

### ARH-28 · 🟡 MINOR · `backend/service/src/sync/sync.service.ts:526-553,607-617`

### SEC-01 · 🔴 CRITIC · `backend/service/src/auth/auth.guard.ts:137-151`

**AuthGuard accepts subject-less HS256 tokens (Supabase anon/service_role API keys) as authenticated sessions, skipping the active-user check**

- **Arie:** Auth / JWT verification  ·  **Sursă:** finder `sec-backend-authz`  ·  **Încredere (self-report):** medium
- **De ce e o problemă:** The active-user/org-hydration check only runs `if (role !== 'super_admin' && sub)` (line 141).
